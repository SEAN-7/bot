---
name: context
description: Reset or compact working context; prepare memory and channel context without losing the current turn.
---

Run `bot-app context reset '{}'` when the working context is confused or a summary is unreliable and you want a fresh start without another summarization call. Before the next model response it discards the generated summary, pending compaction and partial summary work, omits older working history, and refreshes the frozen saved-memory block. It retains the latest input and all its tool activity, extending that boundary when needed to keep tool calls and results together. Reset cannot shrink that retained turn. Saved memory, the complete journal, channel messages, credentials and external work remain intact. A reset does not revoke permissions or undo actions. Recover needed evidence using the memory or communication apps before repeating work or asking for an approval already given.

The reset boundary survives retries and restarts. Later compaction, including `compact '{"rebuild":true}'`, only processes working history after that boundary, so discarded context does not silently return. Journal search and exact reads still cover the entire conversation. Reset also works when automatic compaction is disabled. It does not erase incorrect saved memory; inspect and correct that separately with the memory app when needed.

Run `bot-app context compact '{"keepRecentGroups":1}'` to request compaction before the next model response. It preserves the current input and complete tool call/results. The journal is never deleted. Compaction cannot shrink the active turn alone; reduce shell output or choose a larger model when that turn exceeds the input budget. A request survives provider failure and is retried on the next context preparation.

Automatic compaction is checked before every model call. The default trigger is the smaller of 75,000 estimated tokens and the model-derived budget: 50% of a large context window, or 75% for windows below 512,000 tokens, allowing for output. Context app settings `maxInputTokens` or `maxInputChars` override the trigger. Estimates use serialized JSON characters / 4 and reserve space for tools, saved memory, system framing and output. The current request and all its tool activity stay intact, even when larger than the preferred tail.

Compaction reads the full content, tool arguments, results and source metadata of older journal records before replacing them with a structured summary. Tool output can contain human messages; notification roles do not establish who spoke. Summaries preserve requests, decisions, permissions, outcomes, uncertainty, and journal IDs. Native provider replay data (including signatures and private reasoning) stays in the journal and is excluded from summary input. Nothing else is sampled or silently truncated. Evidence that exceeds the model input budget is processed in ordered batches, carrying the summary forward. Completed batches are checkpointed separately; interrupted or long preparations resume only if their source evidence still matches. A new explicit compact request clears that partial checkpoint. Recent complete tool groups and the current input remain exact. Only a fully successful, usable result replaces the saved summary; failure preserves the prior summary and pending request.

To repair an inaccurate summary, run `bot-app context compact '{"rebuild":true}'`. The next preparation rebuilds from original journal evidence instead of carrying forward the old summary; it still retains the current turn. This can take multiple model calls for a large history. It never rewrites or deletes original messages. Recover precise details using `bot-app memory search` and paginated `bot-app memory read`. Absence from a summary or saved notes does not establish that a fact or authorization was never provided.

The default recent tail targets 2.5% of the model input window, normally 10,000–25,000 tokens, capped at 20% of the window and the configured compaction budget. It prefers at least 20 messages while that fits, and aligns boundaries to complete tool groups. `keepRecentGroups` overrides this preference; a manual compact request defaults to one recent group. A small opening exchange is retained when there are other older groups to summarize; an oversized opening is summarized so it cannot prevent compaction forever. Full active-turn retention preserves the request across long tool loops.

Saved memory is separate from the conversation summary. Successful compaction advances a durable boundary and refreshes this app's frozen memory snapshot for the next model request. Retrying or restarting does not lose that snapshot. Compaction does not automatically write conversation facts into saved memory; use the memory app for that.

Before each model response, this app prepares a short usage snapshot in the journal, e.g. `History ~57323/1000000 tokens; prior input 37549.` Earlier snapshots remain at their original positions until normal compaction. History is estimated from JSON characters / 4, counting native assistant content once and excluding the system prompt and tool schemas; prior input includes cached tokens from the preceding model call. `?` means unavailable. Growth between snapshots is normal. Retries without new activity reuse the last snapshot. The model adapter presents these records as system messages.

`bot-app context prepare --stdin` is the default controller preparation hook. Its settings select `contributors` (such as memory and skills), `projections` (such as chat and Telegram), and `modelApp` for compaction. Set `compaction:false` to retain projections and contributions without summarizing. System contributions live in this app's durable `promptSnapshot`, separate from compactable history. Ordinary contributions use the public `botctl APP contribute` command. The output contains `messages`, `tools`, `settings`, `systemContext` and optional `append` records; the controller journals the latter before completion.
