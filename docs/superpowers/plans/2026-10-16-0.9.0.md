# 0.9.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship 0.9.0 of the agent harness: the eleven decisions in the design plan, removing about 1,600 lines by handing messaging to the filesystem, users to `useradd`, image limits to the plugins and upgrade notices to the agent.

**Architecture:** The daemon (`bot/internal/daemon`) keeps its shape: one poll loop, one goroutine per agent, every file access inside a home through that agent's `fsio` helper. Each task removes one mechanism and the state that served it, updating the manual and spec in the same commit so `TestManualQuotesTheHarness` stays green. Tasks are ordered so the tree builds and tests pass after each.

**Tech Stack:** Go 1.27 standard library only; `/bin/sh` for `install.sh` and `release.sh`; systemd, `useradd`, `userdel`, `setfacl` on the VM.

**Spec:** `bot/docs/plans/0.9.0.md` (the design), which argues from `bot/docs/spec.md` and `bot/docs/philosophy.md`.

## Global Constraints

- Go standard library only. `go vet ./...` and `go test ./...` pass in `bot/` before every commit; `sh scripts/release_test.sh` passes before the release.
- Work on branch `0.9.0`, one commit per task, merged to `main` by pull request at the end.
- Every string the harness shows an agent lives in `internal/daemon/messages.go` or `internal/proto`, and the manual quotes it; `TestManualQuotesTheHarness` lists them all.
- A fact lives in `docs/manual.md` (what agents can observe) or `docs/spec.md` (what they cannot), never both.
- The cached prompt prefix (`SystemPrompt`, `OwnerHeader`, `proto.ShTool`) does not change.
- Nothing suggests to agents that they check the version or the release notes.
- Agent-facing changes are recorded as facts in `internal/notes/notes.md` under `## 0.9.0` (Task 18).
- Privilege tests (`AGENT_ROOT_TESTS=1`, root, Linux) cannot run on the development machine; CI runs them. Each task that touches them says what CI must show.

## Review Focus

1. A message file written by a user that is neither the parent nor a running child, such as a grandparent or a user whose uid was recycled, must be labelled `data` (Task 14a test `TestLabelOtherUidIsData`).
2. A control directory that gains its `config.json` while the previous holder of its name is still being removed must not share that user: the old removal finishes, then a fresh user is created (Task 12 test `TestRecreatedControlDirGetsFreshUser`).
3. `setfacl` failing, because the `acl` package is missing, must not admit a child whose messages can never reach its parent: admission fails, is logged once and retried (Task 14b test `TestGrantFailureHoldsAdmission`).
4. An image larger than the inbox read limit must never reach the plugin truncated: it is a binary note (Task 8 test `TestClassify` case `oversized image is binary note`).
5. A provider answering `invalid_request` on a run's first call must stop that run, write `ERROR` and not retry, and the next successful call must clear it (Task 7 test `TestInvalidRequestEndsRun`).
