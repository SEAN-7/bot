# Plan: 0.9.0, the harness hands work back to Unix and the plugins

Status: planned. Builds on 0.8.0. The harness is 4,988 lines of Go
outside tests and plugins; this plan removes about 1,600 of them by
applying the philosophy's test to each mechanism: if the kernel, the
agent or the plugin can do it, the harness does not. What stays is what
protects a guarantee: privilege separation, journals, crash recovery,
context resets, stray killing and the graceful stop.

Decisions taken while planning, so they are not reopened:

- Images stay; their limits move to the plugins (section 9).
- Stray-process killing stays: it protects a guarantee in the philosophy.
- The graceful drain stays: one 15-minute wait per upgrade is cheaper than
  every busy agent rebuilding its context.
- The 0.8.0 dot-file rule stays (section 6).
- Nothing suggests to agents that they check the version or the notes
  (section 4). The manual states facts; what to do with them is theirs.

## 1. Messages are files the sender writes into the recipient's inbox

Today a message is a spool file the daemon copies into an inbox, records
in `delivered.jsonl`, logs in `messages.jsonl` and removes. From 0.9.0 the
sender writes into the inbox itself, and the label is the file's owner,
which the kernel sets and nobody can forge.

- An agent's `inbox/` is created mode 1770: its group, the ancestors, can
  write into it; the sticky bit stops anyone removing or renaming another's
  file. Its parent, a member of its group, writes messages straight in.
- At admission the daemon grants the child `wx` on its parent's `inbox/`
  by running `setfacl -m u:USER:wx ~/inbox` as the parent through
  `shell.Run`, and links `~/owner` in the child's home to that inbox. At
  removal it revokes the grant the same way (skipped when the parent is
  being removed too; a failure is logged once and retried each poll). A
  top-level agent has no `~/owner`: root has no inbox, and the human reads
  the agent's home.
- The sender stages the file elsewhere and renames it in: an agent in its
  own home, root in the child's home directory. `/home` is one filesystem.
  The README's `send` function writes `/etc/agent/agents/NAME/home/.f`
  and moves it to `home/inbox/f`.
- Collection labels each file by the uid `list` reports: the parent's uid
  (0 for root's children) is `owner`, the uid of one of the agent's
  admitted children is `agents/NAME`, anything else is `data`. Each
  agent's uid is recorded at admission; the parent's is looked up once per
  collection.
- The 64 KiB message limit and both truncation notes go; the inbox clip
  applies as to any file. "Message to NAME dropped" goes: a file written
  into a directory that is not a running subagent's inbox is the writer's
  problem, and `~/.messages/agents/NAME/` no longer exists.
- Remove `conversation.go`, `owner.go` (the delivery record), the
  `delivered`, `unremoved`, `retries` and `spoolIgnored` state in
  `daemon`, `Layout.DeliveredFile` and `Layout.ConversationFile`, the
  `.messages` entries of `harnessDirs`, root's spools in `Run` and
  `install.sh`, and `MsgTruncatedUp`, `MsgTruncatedDownFmt` and
  `MsgUndeliveredFmt`. Existing `.messages/` directories are left alone,
  like any file the harness does not own.
- Manual: "Messages" is rewritten around `~/inbox` and `~/owner`; "Your
  home" gains `owner` and loses `.messages/` and `inbox/.tmp/`; the inbox
  record's `from` rule becomes the uid rule. Spec: the "Messages"
  section becomes the mechanism above; "Conversations are pull, not push"
  and the conversation-log row go. README: "Talk to it" writes into
  main's inbox and reads main's home; `messages.jsonl` is gone.
- Labelling by uid cannot be tested without real users, so the label
  tests move to the privilege tests; unprivileged tests see every file as
  `owner`, since every agent shares the test's uid.

## 2. A user per agent

Today `install.sh` creates `agent-1` to `agent-16`, the daemon hands them
out and `pool.json` records who holds which; a lost or stale `pool.json`
can wipe a live agent's home. From 0.9.0 the daemon creates a user at
admission and deletes it at removal, and the passwd file is the only
record.

- `System.AddUser(name, id)` runs `useradd --no-create-home --home-dir
  /home/NAME --user-group --shell /bin/bash --comment ID NAME`; the GECOS
  field holds the agent id, so `getent passwd` shows which agent a user
  is. `PrepareHome` makes the home as today. The name is `agent-N` for
  the lowest N no user has, so names stay readable; reuse of a name after
  `userdel` is fine, since the user is new.
- `System.Users()` lists the users named `agent-N` with their ids, read
  from `/etc/passwd` (ten lines of parsing; `os/user` cannot enumerate).
  An agent's user is the one whose id is its own. A control directory
  whose id has a user is a restart (home kept); one without is admitted
  with a new user if it holds a regular `config.json`.
- `max_agents` is checked against the number of agent users that exist.
  `settings.json` keeps `max_agents` and is read once at startup
  (section 7).
- Removal, deepest first as today: disable lingering, remove the
  crontab, stop the user manager and kill its processes, sweep the shared
  temporary directories as the user (section 8), hand the journals to the
  nearest remaining ancestor's group, revoke the ACL on the parent's inbox
  (section 1), then `userdel -r`, which removes the home and the group
  and takes the user out of every other group. A failed step is logged
  once and the removal retried each poll; a user whose control directory
  is gone at startup is removed the same way.
- Remove `pool.go`, `poolLost`, `poolUsers`, the reclaiming state and
  `sweep`'s pool scan in `reclaim.go` (`orphaned` now asks `Users()`),
  `Layout.PoolFile`, `Layout.PoolUsers`, `Config.PoolUsers`, the pool
  loop in `install.sh`, the README's "If pool.json is lost" and the two
  known limits about restored backups. `controlDirGone` and `ctrlID` stay:
  a control directory created again is still a new agent.
- Migration, in the daemon, once: if `pool.json` exists at startup, give
  each `active` entry's user its id with `usermod -c ID USER`, remove each
  `reclaiming` entry's user and each pool user with no entry
  (`userdel -r`, their homes are empty), then remove `pool.json`. The code
  goes in 0.10.0. `install.sh` stops creating pool users and keeps the
  0.4.1 floor.
- Privilege tests create and delete real users under a test prefix
  (`Config.UserPrefix`, `agent-test-` in CI, which already runs them as
  root); the fake `System` records the calls.
- Manual: "You" loses "from a fixed pool that is reused"; "Subagents"
  loses the pool wording and keeps the stale-grant warning, since uids
  recycle as they always have. Spec: "Each agent is its own Unix user"
  becomes the mechanism above; the `pool.json` row and "Pool" prose go.

## 3. Plugins install from anywhere

The checksum index compiled into `agent` only accepts this repository's
release plugins. From 0.9.0 root installs any plugin it chooses, as it
installs any package.

- `agent provider install NAME SOURCE`: SOURCE is a path or an `http(s)`
  URL, fetched with `net/http` into memory (64 MiB limit). The rest is as
  today: install for `agent-provider`, `describe`, prompt for settings,
  write the credentials file, refresh `providers.json`.
- Remove `plugins/index.go`, `plugins/index.json`, `verify` in
  `internal/cli/install.go`, the index block in `scripts/release.sh` and
  `TestIndex`. `release.sh` still builds and publishes the plugin assets
  and now writes their checksums into `install.sh`'s block beside the
  agent's; `install.sh` verifies the release's own plugins with
  `sha256sum` before calling `agent provider install`, so a fresh install
  is as pinned as before.
- The protocol becomes a public contract: the "Plugin protocol" section of
  `docs/spec.md` moves to `docs/plugins.md`, which the README links, with
  the `invalid_request` kind of section 5 and the image rules of section 9.
- README: "add another provider later" becomes the two-line download and
  install, or one line with the URL.

## 4. No upgrade notes

The daemon no longer writes `<time>-harness-upgrade.md`. The facts an
agent needs are already on disk: `~/manual/version`, `~/manual/notes.md`,
and the `version` in each run's `start` record.

- Remove `upgradeNote`, `parseVersion`, `less`, `notesSince`,
  `lastDeliveredNotes`, `journal.LastVersion`, `Config.ReleaseNotes`,
  `MsgUpgradeFmt` and `MsgUpgradeSinceFmt`, with their tests.
- Manual: "Upgrades" shrinks to the sentence that the `start` record
  holds the version and that `~/manual/` describes the running one. The
  seed README is unchanged. The header of `notes.md` stops saying the
  daemon delivers sections.

## 5. One configuration check, and `invalid_request`

- The gate reads `config.json` and checks only that the provider is in
  `providers.json` and the model is one of its; no plugin runs at a run's
  start. `plugin.Validate` loses its option branch; `ValidateCached` and
  the admission pre-check (`startingConfigError`, `configTooLarge`,
  `errConfigTooLarge`, `MsgConfigTooLarge`, the `heldBackPrefixes` entry)
  go. A `config.json` over 1 MiB fails the gate's read like any other
  unreadable file. `LoadProviders` stays for the gate.
- A subagent with an invalid config is admitted, gets its user, and
  reports through its `ERROR` and the parent's inbox as any config
  problem; the parent fixes it by removing and recreating the directory.
  The manual's "Subagents" says so.
- Protocol: a plugin answers a request its provider rejects as malformed
  (a bad option, a 400 that is not an overflow) with `kind:
  "invalid_request"`. The daemon does not retry it: the run ends with
  reason `invalid`, `ERROR` gets "Provider rejected the request: MSG", and
  the next successful call clears it. On a run's first call that is the
  config error path. The anthropic plugin maps `invalid_request_error`
  and the openai-compatible plugin maps HTTP 400, overflow excepted.
- Manual: "Configuration" loses the option check and the "told once per
  distinct content" clause; "Runs" gains the `invalid_request` ending and
  its `ERROR` string.

## 6. Staging in the home

The harness stages the files it writes into an inbox as a dot-file in
the agent's home, not in `inbox/.tmp/`, and renames it in. The 0.8.0
rule is unchanged: a dot-file in `inbox/` does not wake but is delivered.

- Remove `inboxStage`, `clearStage`, the `inbox/.tmp` entry of
  `harnessDirs` and the recreate-and-retry in `writeInbox`; `WriteStaged`
  keeps its `stage` argument, now the home.
- Manual: "Your home" loses `inbox/.tmp/`; "Messages" tells senders to
  stage outside the inbox (section 1). Notes: `inbox/.tmp/` is no longer
  used; one left over is the agent's.

## 7. Three simplifications

- `settings.json` is read once at startup. Remove `loadSettings`,
  `settingsErr` and the per-poll reread; a change needs a restart, which
  the spec says.
- `readOwner` reads `OWNER.md` through the parent's helper and uses it if
  it is a regular file; anything else, or a read error, is reported as
  today. Remove `checkSafe`, the directory check and the symlink check.
  The manual's "Owner's instructions" drops the ownership and mode rule.
- `ERROR` holds the latest cause. The gate and the provider retry write
  it; a successful run start removes it whatever it holds. Remove
  `ensureError`, `clearError`'s prefix argument, `errProviderPrefix`,
  `errGuardPrefix`, `heldBackPrefixes` and `clearHeldBack`'s prefix loop.
  The manual's "ERROR" says the file holds the most recent cause.

## 8. A smaller file helper

- Operations: `list`, `read`, `write` (staged), `mkdir` (with a mode,
  then `chmod` to it, so 1770 survives the umask), `rename`, `unlink`,
  `symlink` (remove, then create) and `stat`. Remove `clear`,
  `purge_owned`, `remove`, `private`, `removeAll` and `writable`.
- `seed` makes each harness directory with `mkdir`; one that exists as
  something other than a directory the agent owns is an admission error,
  logged once and retried, not a warning the daemon tracks. Remove
  `unclosed`.
- Removal sweeps `/tmp`, `/var/tmp` and `/dev/shm` by running, as the
  user and after its processes are dead, `find DIR -mindepth 1 -maxdepth 1
  -user "$(id -un)" -exec chmod -R u+rwX {} + -exec rm -rf {} +`. The home
  goes with `userdel -r`.
- Spec: the helper's operation list is updated.

## 9. Image limits belong to the plugins

- `classify` detects the media type. A file whose type the model's
  `image_types` lists is shown as an image, bytes unchanged, with a copy
  in the journal; its content is "[TYPE, N bytes, shown below]". Any other
  non-UTF-8 file is the binary note. Remove the size, edge and decode
  checks, `imageExt`, the 20 MiB budget, `imageBytes`, `Config.ImageBudget`
  and the six notes they produced; the journal's `image` field keeps
  `media_type`, `bytes`, `sha256` and `copy`.
- The anthropic plugin replaces an image over 5 MiB, over 8000 px a side
  or undecodable with a text block "[image not shown: REASON. File:
  PATH]", so the request still goes through. The openai-compatible plugin
  declares no image types and is unchanged. `docs/plugins.md` states the
  rule: a plugin takes what it declares and explains what it drops.
- Manual: the image paragraph in "Runs" shrinks to the type rule, the
  shown note and the binary note; what a plugin drops is in the plugin's
  own words.

## 10. Bugs fixed on the way

- `collectInbox` sends the records it has when a late rename fails,
  instead of ending the run with the moved files unseen.
- Parent notes name the subagent, not its full id.
- `journal.Latest` reads the last line, not the whole file.

## 11. Docs, notes and release

- Spec and manual edits are listed per section; `TestManualQuotesTheHarness`
  enforces the manual. `philosophy.md` keeps every guarantee; "Everything
  that happens is a file in an inbox" now holds more literally.
- `notes.md` gets a 0.9.0 section with the facts: where messages go,
  `~/owner`, no `~/.messages/` collection, no upgrade notes, no
  `inbox/.tmp`, the image note, `invalid_request`, one user per agent.
- Expected size after the change: about 3,300 lines of harness Go, with
  tests shrinking in proportion. The plugins gain about 20 lines.

## 12. Deployment

- Before deploying, a read-only look at main's scripts for `~/.messages`:
  it almost certainly replies there. With no upgrade note, the human sends
  main a message after the upgrade saying where to leave replies and that
  `~/.messages/` is no longer collected. Messages labelled as the owner's
  come from the human.
- `install.sh` 0.9.0 upgrades in place; the daemon migrates `pool.json`
  at its first start (section 2). Verify with `getent passwd agent-1`
  showing main's id and `journalctl -u agent` showing the migration line.
